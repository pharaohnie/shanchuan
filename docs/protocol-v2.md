# roomId 协议 v2 设计（只设计，未实现）

状态：草案，供评审。本文不改变现有代码行为。

## 1. 现状

加入房间的 ID 由口令直接派生：

```text
roomId = SHA256("croc-wasm/room/v1" + code)[0..32]   // 64 位十六进制
```

- `code` 是 12 位、字符集 62 的口令，熵约 `log2(62) * 12 ≈ 71.5 bit`。
- 中继在 join 时能看到完整 `roomId`，并会写入日志。
- PAKE 保护的是“不知道口令的中继不能解密/冒充”，但 `roomId` 本身是一个**离线口令验证器**：拿到日志的人可以对候选口令做一次 SHA-256 就能判断对错。
- 一旦口令被离线枚举出来，再配合录到的 PAKE 报文，就能重建会话密钥并解密当时的内容。PAKE 不能阻止这种“先录后破”的攻击。

所以问题不是“PAKE 不够强”，而是“roomId 把口令变成了一个可离线验证的哈希”。

## 2. 目标与非目标

目标：

1. 只拿到中继日志（含 roomId 和 PAKE 报文）的人，不能以可接受成本离线还原口令。
2. 保留“双方只输入同一个口令就能配对”的现有 UX，至少作为可用路径。
3. 不重写 PAKE，不更换 AES-GCM，不引入新的运行时依赖。

非目标：

- 不防御已经拿到口令的人。
- 不防御恶意中继做在线冒充（PAKE 已经处理）。
- 不解决终端被控、浏览器扩展、屏幕录制等端点问题。

## 3. 两条候选路线

### 路线 A：服务端每会话随机盐 + HMAC

```text
salt   = relay 为每个房间生成的 128-bit 随机值
roomId = HMAC(salt, code)
```

直觉是“加盐后彩虹表失效”。但需要解决一个先后顺序问题：

- 接收方必须先知道 `salt` 才能算出 `roomId`，而它此时只知道口令。
- 如果 `salt` 由中继按 `code` 查询，中继就需要一个 `code` 的派生索引；这个索引本身又是离线验证器。
- 如果 `salt` 放在邀请链接里，那链接已经携带了一个随机值，安全性等价于路线 B 的随机令牌，盐只是附加品。
- 如果 `salt` 是全局固定值，它只能防跨部署的预计算，不能提高单次猜测成本。

结论：**仅加盐不改变离线猜测的每次尝试成本**（HMAC 和 SHA-256 一样快），主要价值是防预计算和防跨会话关联。要真正提高成本，必须把派生函数换成慢 KDF（例如 PBKDF2/Argon2），这属于路线 A 的增强版，而不是“加盐”本身。

### 路线 B：邀请链接携带随机 room token

```text
roomId = 128-bit 随机 token（由发送方生成，放在邀请链接/二维码里）
code   = 仍然只用于 PAKE
```

- 中继日志里只有随机 token，和口令没有函数关系，无法离线验证候选口令。
- 需要双方都拿到 token。只手工输口令的接收方无法定位房间。
- 令牌在 URL fragment（`#` 后面）里不会发给服务器；但仍会进入浏览器历史、剪贴板和聊天记录，需要提示用户。

### 路线 C：服务端口令→token 查询（可选折中）

接收方输入口令，向中继换取 room token，中继对查询做严格限流。这样保留手工输码 UX，但：

- 中继需要保存“口令派生索引 → token”的映射，这个索引又是离线验证器；如果中继本身不可信，问题只是从“日志泄露”变成“中继主动作恶”。
- 要避免索引泄露，需要 OPRF 之类的盲化查询，复杂度和依赖都会上升。
- 中继因此知道谁在找哪个房间，元数据更多。

本方案暂不推荐，只作为后续选项记录。

## 4. 对比

| 维度 | 现状 v1 | A：随机盐 + HMAC | A+：盐 + 慢 KDF | B：随机 token 链接 |
| --- | --- | --- | --- | --- |
| 日志能否离线验证口令 | 能，一次 SHA-256 | 能，成本不变 | 能，但每次尝试更贵 | 不能 |
| 防预计算/彩虹表 | 否 | 是 | 是 | 是 |
| 手工输码 UX | 保留 | 保留（但需解决取盐） | 保留 | 失效 |
| 中继改动 | 无 | 需发盐/查盐 | 同 A | 无（roomId 仍是不透明字符串） |
| 兼容旧客户端 | - | 需协议版本 | 需协议版本 | 需邀请链接与新入口 |

## 5. 建议

分两步，不一次梭哈：

### v2.0：不改变 UX，先把离线猜测变贵

保持 `roomId` 由口令派生，但把 SHA-256 换成 WebCrypto 自带的 PBKDF2-HMAC-SHA256：

```text
roomId = PBKDF2(code, "croc-wasm/room/v2", iterations)[0..32]
```

- 迭代次数在低端手机上实测，目标单次派生 150–250ms，建议从 600,000 起步再调。
- 双方都在连接前派生，协议和 UI 不变；中继不需要改。
- 这不会让离线破解“不可能”，但把每次猜测从纳秒级拉到百毫秒级，配合 71.5 bit 口令，成本从“GPU 小时”变成“GPU 世纪”量级。
- 缺点：老客户端算出的 roomId 不同，会和新人错开。需要版本提示（“对方版本较旧，请刷新页面”）并在发布时强制刷新缓存。

### v2.1：增加随机 token 邀请链接，作为强路径

- 发送方生成 128-bit 随机 token，页面显示“复制邀请链接/二维码”。
- 链接形如 `https://host/#r=<token>`；接收方打开后仍需输入口令完成 PAKE。
- 手工输码路径保留 v2.0 的 PBKDF2 派生，并在 UI 标注“手动口令模式的离线强度较弱，推荐用邀请链接”。
- 中继仍然只看到不透明的 roomId，不需要理解 token。

### 不推荐现在做

- 服务端按口令查盐/查 token（路线 C）：元数据和复杂度都不划算。
- 重写 PAKE 或自研 OPRF：超出本次范围，也没有现成依赖。

## 6. 迁移与兼容

1. 新增 room 域常量 `croc-wasm/room/v2`，不复用 v1。
2. 前端发布时更新 `index.html` 的资源版本，避免旧缓存继续用 v1 派生。
3. 握手阶段已有 `proto-hello`；协议 v3 可再带 `roomDerivation: "pbkdf2" | "token"`，但 roomId 在 join 前就要算好，实际只能靠“同版本客户端”或链接参数区分。
4. 回滚策略：保留一个构建开关，遇到兼容问题可临时回到 v1 派生；回滚期间明确提示“未启用 v2 房间派生”。

## 7. 验收（未来实现时）

- 同一口令在 v1/v2 下得到不同 roomId，且 v2 派生在目标设备上耗时符合预算。
- 中继日志中只有 roomId，不出现口令或可离线验证口令的快速哈希。
- 邀请链接路径下，只拿到日志和链接 token 的人无法验证候选口令。
- 旧客户端连新客户端时给出明确版本提示，而不是无限等待。
